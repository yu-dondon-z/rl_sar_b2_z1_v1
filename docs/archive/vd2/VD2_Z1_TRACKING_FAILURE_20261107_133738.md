用户补充：Y 可以正常展开，R1+Y 后立即报错，前面约三次也呈现相同分界。
本轮读取板载已有日志、配置和文件哈希，仅执行 ICMP ping 与本地记录回放。

## 结论及边界

程序的策略接管/机械臂执行接口存在明确不足，不能把现象简单归为网线或 IP 配错：

1. Y 使用 6 秒平滑关节插值，实测反馈持续更新、到位正常。
2. R1+Y 后改用 actor 的位置输出。当前只有关节位置范围限制和 1 秒入口混合，
   没有逐周期的臂目标速度/加速度约束；混合的终点每周期变化，不能保证轨迹连续平滑。
   日志已出现第二关节目标反复换向，与反馈速度和力矩的振荡相伴。
3. 本地 z1_controller 回复持续新鲜，但里面的电机 q/dq/tau 完全冻结。
   当前程序有重复向量诊断，但它只写日志；策略仍会消费缓存的非零关节速度，
   在电机反馈已无变化时继续改写目标，直到控制器退出 LOWCMD 引发 fault 4。

优先怀疑策略位置输出与实际 Z1 动态响应不匹配，在接管时形成振荡并伴随后续臂端通信异常。
这是基于时间顺序和离线回放的判断；**未证明具体的电流保护、供电故障、固件复位或网络丢包机制**。
本轮未抓 8881 UDP，不能证明 0.72 秒时 arm 端确切收到了哪个目标，
也不能把最大目标跳变与同一周期的反馈冻结强行排序为前因后果。

- 第二关节 q = 2.41763 rad，dq = +2.36196 rad/s，tau = +37.83203 Nm。

- 六关节 q/dq/tau 整个向量逐元素完全相同。

不能将冻结区间中的速度、力矩当作此后机器人的真实运动。
`max_arm_error=0.443` 是最后目标 1.97476 与缓存位置 2.41763 的差，
不是“制动时再次跳了 0.443 rad”的证据。

## 哪一段通信正常

主程序 native ↔ 本地控制器在 tracking 直到 fault 期间，发送和回复均约 **497.1 Hz**。
tracking 的本地回复年龄 P95 为 **1.954 ms**，控制周期未见长停顿。
native 最新发送目标的来源年龄 P95 **19.713 ms**，最大 **19.951 ms**，
与 50 Hz 保持上一周期目标的记录方式相符，未见该段队列年龄持续累积。
这不等于 8881 发往 arm 的延迟，也不是电机采样年龄。

板载当前 `192.168.123.110` ping 3/3 成功，约 0.116–0.658 ms；
路由走 eth0，控制器配置仍为该地址、8881。
只能说明检查时 IP 网络可达，不能替代故障时的 arm UDP 证据。

本次 `z1_error`、`z1_connected` 一直全零；电机向量冻结后这些字段也可能是缓存，
不能把全零错误码当作电机仍正常工作的证明。
`fault 4` 来自 `native/io.cpp`：要求 LOWCMD 但收到其他模式持续超过 0.5 秒；
这是控制器在 arm 超时后转 PASSIVE 的后续结果，不是首先发生的网络错误码。

## 已验证的程序问题和仿真差异

### 停止修复生效，问题位于 tracking 阶段

原始输入回放 51 个 braking 周期，机械臂目标最大相邻跳变为 **0**。
tracking 目标回放误差 <1.67e-7 rad，原始动作误差 <7.16e-7。
此前修复的制动参考保持有效，这次不能继续归因于旧的停止目标跳变。

tracking 内末端 xyz 命令每周期最大变化仅 **3 mm**；大关节跳变来自
actor 输出及其对实际关节反馈的响应，不是视觉直接发送了 0.42 rad 的关节指令。
1 秒入口混合无法抑制其中的快速变化。

对固定日志观测做离线敏感性复算：0.720 秒原始 actor 第二关节目标为 1.98936 rad；
只把观测副本中的六个臂速度替换成上一周期对应值，输出变为 2.48519 rad。
原始模型输出与记录一致。该实验支持速度反馈参与输出振荡，
**不是闭环稳定性验证，也不支持在真实观测中填零或伪造速度**。

### 训练执行器条件与部署不同

核对了对应检查点保存的 params/env.yaml，而非仅查看当前训练源文件：

- 六轴均为 ImplicitActuator，stiffness=160、damping=5。
- effort_limit_sim 均为 **120 Nm**，velocity_limit_sim=3.1415 rad/s。
- 部署 URDF 的第二关节 effort=60，其余关节 effort=30。
- 实机使用原 SDK 原始 K_P=[20,30,30,20,15,10]、K_W=[2000,...]。

URDF effort 字段不是实测固件保护阈值；SDK 原始增益也不能直接当作上述仿真物理增益。
但这已经是可核对的执行器建模差异，不能以 MuJoCo 通过作为实际 Z1 输出可执行的证明。
本轮没有更改增益。

### 后视另有实际几何拒收

停车 seq 94 的实际帧年龄约 **0.377 s**，不是上一轮的 1 秒旧帧超时。
直接深度支撑 x 范围约 **[-0.88483, -0.63598] m**，不包含工作点 -1.02 m。
原始浮点深度及 RGB 离线复算得到完全相同的拒收原因；
前视仍有效。相邻 seq 93 和 95 有有效工作点支撑。
不能通过延长帧时效或伪造支撑点修复本帧几何问题。
它导致停车，但时间上晚于电机反馈冻结。

## 建议的下一步

先处理软件接管与执行器接口：

1. 将臂目标生成和实际执行分开，原始 actor 历史保留，输出侧提供连续的关节位置/速度/加速度轨迹；
   根据真实响应确定边界，并在仿真、实机使用相同逻辑。不能仅给代码加一个任意低通后宣称修好。
2. 区分本地控制器回复与电机数据更新，把已观察到的“持续报运动但向量冻结”纳入实际故障处理，
   不继续把缓存速度反馈进策略；不伪造时间戳、接触或观测。
3. 用录制输入回放与匹配执行器模型做闭环验证，再经现场确认进行最小运动验证；
   届时同时记录本地 SDK 与 arm UDP，才能裁决臂端停止回包的机制。
4. 后视的有效深度覆盖单独处理，不能让它掩盖先发生的机械臂异常。
