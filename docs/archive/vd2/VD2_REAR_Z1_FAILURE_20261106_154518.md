## 两个需要分开处理的问题

### 后视的有效测量片段太短

第 57 包后视返回 `geometric seam path is too short`，对应
`dual_camera_perception.py::_path_result` 的有效三维路径长度不足 0.12 m。
保存 RGB 中能看见整条黑胶带，不代表该线段都有可信深度、地面支持及神经中心线。
现有处理在成功帧中也常只保留约 0.15 m 的有效片段。

停车时新包年龄约 0.55 s，上一次可信后视测量年龄已约 1.018 s，超过原 0.6 s
后视保持窗口，因此停车。单纯加等待会继续使用更旧测量。
视觉包总体处理 P95 约 548 ms：前视约 366 ms，后视约 180 ms；
两者是各自 P95，不能相加当同一包时长。原实时耗时问题仍有余量风险。

稳态下后视深度拟合地面法向与同期 IMU 竖直相差约 7°，停车后增至约 16–20°。
这是需要核查外参、深度质量、平面选择及地面假设的诊断量，不能从它直接断言
外参错了固定角度，更不能用该角度自动修改实机标定。

第 57 包导致停车的具体图像没有单独保存；目前保存的最近有效图是第 55 包，
最后一般图是第 61 包。后续应保留触发停车的原 RGB-D，避免对邻近有效图的复算
被误认为已复现和修复该失败包。

### Z1 电机数据断流，而 SDK 控制器仍回复

六轴 q/dq/tau 从约 24.587 s 起到退出，连续约 2.700 s 完全相同；
其中 dq 仍含非零值（例如第 4 轴约 -1.464 rad/s），这不是正常静止量化可解释的现象。
控制器输出连续 `connect with z1_arm wait time out`，继而
`Lose connection with z1_arm`、`lowCmd to passive`。

数据停止更新比后视停车早约 0.56 s。不能认定是停车流程导致电机通信中断，
也不能仅凭时间接近就认定视觉导致通信中断。

`native/io.cpp` 当前 `state.z1_time` 取自 127.0.0.1 SDK UDP 回复时间，
因此 `z1_age_ms` 很小只证明板载与 z1_ctrl 间的本地连接有回复。
它不能证明 `z1_ctrl → 192.168.123.110:8881 → 电机反馈` 这段链路仍在更新。
本次 `z1_error` 与 `z1_connected` 都保持全零，也可能属于同一份旧电机缓存。

fault 4 的实际含义是：程序仍请求 LOWCMD，但控制器返回其他模式持续超过 0.5 s，
见 `native/io.cpp:180`。它不是本次视觉几何错误的编号，也不是直接的过流编号。

目前没有故障时的机械臂 UDP 原始收发记录，无法确定是供电、接插件、机械臂端
通信服务/固件，还是链路丢包。日志中的力矩峰值不能单独证明过流。
故障后开发机 ping 机械臂 IP 3/3 回复，RTT 约 0.09–0.13 ms；
这只能说明检查时 IP 可达，不能证明故障时 UDP 或电机状态正常。
读到的 eth0 RX 计数在后续检查变小，累计计数不能用作本次故障期间的丢包统计。

## 下一步取证

输出文件由 mktemp 唯一创建，不覆盖旧抓包：

```bash
z1_capture=$(mktemp /home/unitree/rl_sar_b2_z1_VD2/runs/z1_arm_XXXXXX.pcap)
printf '%s\n' "$z1_capture"
sudo timeout -s INT 45 tcpdump -i eth0 -nn -s 0 -U -w "$z1_capture" \
  'udp and host 192.168.123.110 and port 8881'
```

需要在实际故障发生时记录才能区分：板载是否持续发包、机械臂是否返回、
返回是否有长间隔。当前控制程序关闭时空抓包不能复现运动期间的问题。
下一次还应给启动器控制器日志增加单调时钟接收时间，并保存触发后视停车的原始图，
这些是诊断记录，不应通过修改增益、放宽旧帧年龄或伪造电机时间来代替。
