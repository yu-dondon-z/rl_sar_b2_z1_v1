## Z1 指令迟滞与制动目标跳变

按板载控制器 `include/message/arm_common.h` 解码原始 arm UDP：
每个指令关节 20 字节，字段为 `T, W, Pos, K_P, K_W`；
六关节实际发送 120 字节。每个状态关节 22 字节，实际回复 132 字节。

将每次变化的六关节 Pos 与 Python `target_q[8,13,14,15,16,17]` 匹配，
可确认报文中的目标对应较早的控制周期：

| 报文时间区间 | 成功匹配的目标变化数 | 从记录时刻到 arm 发包的延迟：最小 / 中位 / 最大 |
|---|---:|---|
| 11.2–13.0 s | 85 | 75.98 / 84.00 / 96.71 ms |
| 13.0–15.0 s | 98 | 84.87 / 92.80 / 105.87 ms |
| 15.0–17.0 s | 98 | 93.86 / 100.53 / 112.95 ms |
| 23.3–23.6 s | 6 | 137.42 / 140.97 / 147.62 ms |
| 24.8–25.0 s | 8 | 141.98 / 144.56 / 154.17 ms |

时间差包含该 Python 周期内目标计算时间，不是严格的纯网络延迟。
本次未抓本地 8071/8072 流量，不能将全部迟滞定位到 SDK 队列、
控制器收包或某个线程。正常状态回复到 Python 的对应差多数只有几毫秒，
tracking 中位约 4.70 ms，与指令方向约 140 ms 不是同一量。

具体的制动目标异常：第 2 关节在 `t=24.790374 s` 请求 `2.671740 rad`，
`t=24.810358 s` 又请求 `2.227770 rad`，约 20 ms 内变化 `0.443971 rad`，
约 25.44 度。不能把它误称为实际关节在 20 ms 内转了 25 度。
此时实测关节速度和力矩也明显振荡。
`return_stand` 已锁定后一个目标，但 `t=24.935423 s` 发往 arm 的仍是前一个大目标，
直到最后正常回复之前仍在发送它。
这支持“目标变化大、发往 arm 的目标滞后，可能共同恶化闭环响应”的判断，
尚不足以证明某次跳变直接导致后续掉线。

## Z1 最后发生了什么，仍缺什么

异常前板载与机械臂仍持续双向收发。
tracking/制动末段没有先出现 100 ms 级 arm 回复空窗。
最后正常回复 `t=24.941449 s`；最后异常回复 `t=24.945636 s`：

- 第 2 关节第二个电机状态报告 `connected=1`。
- 第 3–6 关节各第一个电机状态报告 `connected=1`。
- 原始定义为 `0=正常，1=断连，2=CRC 错误`。
- 主程序 `z1_connected` 随后变为 `[0,0,1,1,1,1]`，触发 fault 7。
- SDK 这时仍保留部分最后正常关节测量值，不能将该包异常的位置突跳当作真实关节运动。

之后不再捕获 arm 的回复，板载仍持续发送到 `t=26.050480 s`。
所以本次不能解释为“Python 主程序先停止发包，才使机械臂最初报错”。
后续 `z1_sdk timeout` 发生在主程序故障退出以后，不能倒置为首因。

本次没有触发“q/dq/tau 完全不变却持续报告运动”的重复向量诊断，
与上一会话长时间保持同一反馈向量的现象不同。
B2 日志未见电机错误码；Z1 日志的 error 字段为零。
原始状态正常包和异常包都有 `0x40`，它不属于本地故障掩码 `0x3f`，
现有 SDK 注释也未把它定义为过流；不能据此断言过流或过热。

目前可确定的是“机械臂回复先报告多电机连接异常，随后 arm UDP 回复消失”。
供电、内部电机通信、固件或受控运动引发的保护/重启之间，现有证据不能裁决。
